How Game Pace works

This page explains why the tool exists, the decisions behind it, and how it is built, so anyone who wants to improve it later can start from the same understanding.

Purpose

IFAF video supervisors review game footage and give officials written feedback on mechanics and rule application. Game pace was added as a feedback item: the time between the end of a play and the ready for play (R4P) whistle for the next down. Until now it was timed by hand, which was slow, hard to verify and easy to get wrong when copying numbers into the review sheet.

Game Pace replaces that with a single page where the reviewer watches the game, marks the end of a play and the R4P with the keyboard, and gets live averages that can be pasted straight into the review sheet. Every measurement is tied to a video timecode, so any number in the feedback can be checked by anyone with the link.

What is measured

Each measurement is the elapsed time from the moment the play ends to the R4P signal for the next down. The reviewer classifies every measurement by the situation it follows. The limits below are the acceptable thresholds agreed for feedback; a measurement or average is shown in green when it is below its limit and in red when it is at or above it.

The limits are editable. Change a value in the table and every measurement, average, color, clock warning and exported grade updates immediately, including reviews already in progress. Limits are saved in this browser, so if the criteria change officially, every supervisor needs to update their own copy (or the defaults can be changed in the code, see below).

Measurement method

The central design decision is that the tool measures in video time, not wall clock time. When a measurement starts, the tool reads the exact second the video is at; when the R4P is marked, it reads it again, and the pace is the difference. This means the reviewer can pause, rewind to find the true end of the play, or watch at 1.5x or 2x, and the result is still the time that actually passed in the game. A stopwatch would be wrong the moment the video is paused.

A second consequence is traceability. Each entry stores its start and end positions in the video, so clicking a timecode takes anyone back to that play to confirm the number.

The game start timecode exists for two reasons. Broadcasts usually include minutes of pregame content, and the tool blocks measurements before that point so none are logged by accident. It also lets the tool show game time alongside video time, which makes it easier to orient within the footage.

How averages work

Every measurement has exactly one type (no foul, after TD, after XP/COP, on foul). The last two minutes are not a fifth type but an independent tag, because a play inside the last two minutes can also be a foul or follow a touchdown. Treating it as a tag avoids forcing the reviewer to choose between two true descriptions of the same play.

The general average is the mean of all measurements, each counted once, including the ones tagged as last two minutes. Because the tag does not create a second entry, there is no double counting. Excluding tagged plays would bias the general figure by removing real plays from exactly the stretch where pace matters most.

The general average is deliberately not the average of the category averages. That method would give three foul measurements the same weight as forty regular downs. This was checked against a completed review sheet (Australia v Israel, IFAF World Flag 2026), where the general value matches a weighted mean of all measurements and not a mean of the category averages.

Reviewer workflow

The tool is designed so the reviewer never has to look away from the video. Measurements are driven by the keyboard, and a transparent layer over the player keeps the keyboard focus on the tool instead of letting the YouTube player capture it. When the reviewer needs YouTube's own controls (video quality, captions), a button removes that layer; a warning appears if the shortcuts become paused as a result.

1 2 3 4Start a measurement of that type. Pressing a different number while timing switches the type without losing the start point.

TTurn the last two minutes tag on or off for the next measurements.

← →Rewind or skip 5 seconds; with Shift, 1 second.

Logged entries can be corrected afterwards: type and two minute tag can be changed, the comment edited, and an entry deleted with a short undo window.

Export to the review sheet

Export follows the structure of the IFAF game review sheet rather than inventing a new format.

Averages. Copy averages places the six values on the clipboard in the same vertical order as the sheet, from avg Pace to avg Pace in 2min, so they paste into the pace block in one action. Categories without measurements are left empty. The decimal separator can be set to point or comma to match the reviewer's spreadsheet locale.

Rows. Measurements can be added to the play list of the sheet. Timecodes and the remaining columns are copied separately on purpose: column B holds a formula that builds the video link from column A, and pasting a single block across it would overwrite that formula. Column A receives the timecode in H:MM:SS. Columns C to G receive Mechanics, Crew, an empty Application cell, a grade of IM when the measurement is over its limit or CM otherwise, and the comment. By default only measurements over their limit are exported, since those are the ones that normally deserve a remark.

Comment. The comment is a standardized starting point, meant to be shortened or expanded by the reviewer. It is built from an editable template where {s} becomes the rounded seconds and {type} becomes the sheet label of the type, with "(2min)" added when tagged. The default template produces text such as "24 sec on Pace w/o fouls". An edited comment is kept as written and can be reset to the template.

Assumptions and limitations

The end of a play and the R4P are judgment calls made by the reviewer on what the footage shows. The tool makes the timing precise, but it cannot make those two decisions for the reviewer, and consistency between reviewers depends on applying the same criteria.

Broadcast production can distort pace. If the stream cuts to a replay instead of showing live action, the video time includes the replay and the measured pace is longer than the real one. The tool cannot detect this. Reviewers should delete or correct those entries, or note the circumstance in the comment.

Some channels disable playback outside YouTube. For those videos the tool offers a local file mode, which plays a downloaded copy of the game with the same measurement logic. Since 2025 YouTube also rejects embedded players on pages without a web origin, which is why the tool must be opened from its published address and not by double clicking the file on disk.

Reviews are stored in the browser that was used to create them. They do not sync between computers or between reviewers. The backup buttons exist to move a review to another computer or hand it to another supervisor.

The limits, labels and categories reflect the review sheet and criteria in use when the tool was built (October 2026). Limits can be adjusted from the table above without touching the code; labels and categories still require a code change.

Technical architecture

The whole tool is one self-contained HTML file with inline CSS and JavaScript. There is no build step, no framework, no server and no external dependency other than the YouTube IFrame Player API, which is loaded only when a YouTube video is opened, and two Google Fonts with system font fallbacks. The IFAF logo is embedded in the file as a data URI. This keeps hosting free and trivial: any static host works, and the reference deployment is GitHub Pages.

The video player is wrapped in a small adapter object with the same five methods for both sources: read the current time, seek, play or pause, set the playback rate, and destroy. The YouTube adapter calls the IFrame API; the local adapter drives an HTML5 video element. The rest of the code only talks to the adapter, so adding another source means writing one more adapter.

A timer refreshes the clock display every 100 ms by reading the current video time. The measurement itself never depends on that timer; it only uses the two video positions captured at start and at R4P, so the precision is that of the player's reported time.

Rendering is plain DOM generation from the state object. After any change the state is saved and the affected parts of the page are re-rendered. The page is small enough that this is fast and keeps the code easy to follow.

Data model and storage

Each review is a session object keyed by its video. For YouTube the key is yt: plus the video ID; for a local file it is file: plus the file name and size.

{
  "key": "yt:3ink6ZlQUuU",
  "src": { "kind": "yt", "id": "3ink6ZlQUuU", "url": "https://www.youtube.com/watch?v=3ink6ZlQUuU" },
  "start": 425,            // game start in video seconds, or null
  "two": false,            // last two minutes tag currently on
  "entries": [
    { "id": "m1x2y3", "t0": 577.4, "t1": 598.6,
      "type": "nf",        // nf | td | xp | fo
      "two": false,
      "comment": null }    // null means "use the template"
  ]
}

Sessions are saved in the browser's localStorage under pace:<key>. The key of the last opened session is stored in pace:last so the tool reopens it on load, and reviewer settings (comment template, export filter, decimal separator, custom limits) live in pace:settings. Storage is scoped to the address the tool is served from, so moving the tool to a new address starts with empty storage; backups are the migration path. A backup file wraps the session as {"app":"ifaf-game-pace","v":1,"session":{…}}.

Changing or extending it

Most likely changes only touch two constants near the top of the script. TYPES defines the measurement types: their internal ID, sheet label, button label, shortcut key and limit. STATS defines the rows of the averages table: label, limit and a filter function that selects which measurements count. Day-to-day limit changes are made from the editable table on this page; the shipped defaults live in DEFAULT_LIMITS, and both TYPES and STATS read their limit from the active set, so a new default only needs to be written once. The rule everywhere is that a value is acceptable when it is strictly below its limit. Adding a new type means adding an entry to TYPES with a free key, a matching row to STATS, a default in DEFAULT_LIMITS and an input row in the limits table; the buttons, list, shortcuts and export pick it up automatically. Removing a type requires care with existing saved reviews, which may still contain its ID.

If the session format changes, increase the backup version number and keep the loader able to read older backups.

Before publishing a change, check at least the following by hand: a measurement with a pause in the middle, a measurement at 2x speed, switching type mid-measurement, the game start block, delete and undo, reopening the page to confirm the review is restored, and pasting both exports into a copy of the review sheet. The file can also be checked offline in local file mode with any video.

Ideas that were considered and left for later: excluding an entry without deleting it, editing the start and end points of a logged entry, aggregating several reviews to compare crews across a tournament, and a shared online store so supervisors can see each other's reviews.
